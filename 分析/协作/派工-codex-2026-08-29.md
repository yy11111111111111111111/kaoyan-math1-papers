## 交付方式（因为你推不了云端，这一节决定成败）

**基线**：先确认你读到的是 `f5c0ddc`。若已前移，**以你实际读到的 commit 为准并在报告里写明**，
不要假装是 f5c0ddc——integrator 靠这个判断补丁能不能干净落地。

```bash
git rev-parse --short HEAD    # 报告里写这个值
```

**产出两个独立的 diff，不要合成一个**：

```bash
# 做完任务 A 之后
git diff > /tmp/codex-A-lint.diff
# 做完任务 B 之后（在 A 的基础上）
git diff > /tmp/codex-AB-all.diff        # 或只对 B 涉及的两个文件出 diff
```

为什么必须分开：**任务 A 上线后 lint 会故意变红**（R3 预期报 `calc.mvt-proof/A2`），
任务 B 才把它修绿。合成一个 blob，integrator 就无法验证中间状态、也无法判断
"R3 报出来的是不是正好是预期的那一条"。

**报告**：写成一段 markdown 文本直接给用户（**不要**写进 `分析/审查/`），含
`base_commit` / 每步做了什么 / 三次 lint 结果（A 前、A 后、B 后）/ 注入测试结果 /
你遇到的判断分歧。integrator 收到后会替你归档到 `分析/审查/codex-lint-hardening-<你的 head>.md`。

**尽量让 diff 小**：只改必要的行，不要顺手格式化、不要重排 YAML 键序——
diff 越大，integrator 人工核验的成本越高，也越容易在落地时冲突。

## 任务 A（先做，纯代码，自包含）

**给 `分析/tests/lint_method_families.py` 补两条检查。**

### A1 · guard 字段白名单

**动机**：integrator 上一轮修复时，自己往 guard 里塞了一个 `scope:` 字段——
而 v1.3.1 的 guard 字段集只有 `{condition, logical_role, check, explanation}`。
lint 对 guard 字段没有任何校验，**静默通过**了。这个错误是事后靠人读出来的，
不是靠 lint。同类错误还会再犯。

**做**：加一条 error，guard 出现白名单外的键即报错。白名单以现有 11 族实际用到的键为准
（先跑一遍统计出全集，别凭空定），新增键必须同时升 `schema_version`。

**验收**：注入一个 `scope: A3` 到任意族的某条 guard → 必须 FAIL；移除后 → error 0。

### A2 · R3：mandatory continuation 的可达性

**动机**：mvt 族的 BL-5——`A2` 的 `followup` 是 `mode: all_of`（强制全执行），
其中含 `action_ref: A1`；而 `A2.eligible_cells = [存在性等式, 不等式]`，
`A1.eligible_cells = [存在性等式]`。于是**在不等式格选中 A2 后，强制后继指向一个本格不可用的 action**。
R1 只查 action_ref 是否存在，R2 只查单个 action 与格的一致性，**两条都漏掉这一类**。

**做**：新增 R3——对 `mode` 为 `sequence` 或 `all_of` 的 followup 里的每个 `action_ref`，
其目标 action 的 `eligible_cells` 必须 ⊇ 源 action 的 `eligible_cells`。
（`any_of` 不受此约束——那是可选分支，允许只在部分格可用。）

**验收**：R3 上线后**应当**报出 `calc.mvt-proof/A2`。若还报出别的族，逐条记进报告，
**不要顺手改** artifact——那是内容判断，不在本任务范围。
